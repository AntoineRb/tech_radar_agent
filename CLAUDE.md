- Environment variables (LLM, secrets): `cp .env.example .env` then `uv run --env-file .env tech-radar-agent`. Details: `docs/configuration.md`.
- Test the configured LLM: `uv run --env-file .env python -m tech_radar_agent.llm` (answers "pong") or `... --debug "my question"` (duration + tokens). Codes: 0 OK, 1 LLM error, 2 invalid settings.
- Run the agent: `uv run tech-radar-agent` from the repo root (entry point `tech_radar_agent:main` in `pyproject.toml`, defined in `src/tech_radar_agent/__init__.py`). Reads `config/interests.yaml`, collects into `data/tech_radar.db`, then scores and summarizes (agent loop, `LLM_*`/`AGENT_*` settings read **after** the collection). For real: `uv run --env-file .env tech-radar-agent` (⚠️ calls the LLM: ask me first). Then the digest (selection, rendering, Telegram sending, marking). Options: `--dry-run` (everything except sending: writes `output/digest-YYYY-MM-DD.html`, nothing sent or marked; calls the LLM) `--preview` (the digest alone from the database, without collection or LLM, written to a file) and `--send-only` (the digest of what is already scored, **sent and marked**, without collection or LLM: to receive a digest without starting Ollama). Mutually exclusive options. Exit codes: 0 OK (even if some sources or some articles fail), 1 all sources failed (takes priority), 2 invalid config (nothing collected, no LLM call), 3 collection saved but scoring skipped (invalid or missing LLM/agent settings) or stopped midway, 4 digest not sent or partly sent (priority 1 > 3 > 4).
- View the database: `sqlite3 data/tech_radar.db "SELECT source, count(*) FROM articles GROUP BY source"`.
- Install / sync: `uv sync`.
- Add a dependency: `uv add <pkg>` (or `uv add --dev <pkg>` for a dev tool).
- Always go through `uv`. Never `pip`, never manual venv activation.
- Tests: `uv run pytest` (everything, ~0.3 s), one file: `uv run pytest tests/test_models.py`, one test: `uv run pytest tests/test_models.py::TestArticle::test_defaults`, by name: `uv run pytest -k xxe`. Guide: `docs/development/testing.md`. No linter.

## 🔒 Security (non-negotiable rules)

Details and rationale: `docs/security.md` and ADR 0007. Every new dependency, source or LLM step must follow these rules **before** being coded.

**Dependencies: trusted only**
- Standard library first. A third-party dependency must be justified.
- Before every `uv add`, Claude checks and presents to me: official repository, maintainers, date of the latest release, number of downloads, known CVEs, exact name on PyPI (watch out for typosquatting). I approve before it is added.
- Only from PyPI via `uv`, and `uv.lock` (sha256 hashes) always committed.
- Audit before every MR that touches dependencies: `uv export --format requirements-txt --no-emit-project --all-groups > "$TMPDIR/req.txt" && uvx pip-audit --strict -r "$TMPDIR/req.txt"` (`--all-groups` includes the dev dependencies).
- GitHub Actions: only official or widely recognized actions, pinned to a commit SHA.

**Services and URLs: verified**
- Only official, documented APIs, and RSS feeds published by the publisher's official site. Each source is documented with its official documentation link in `docs/architecture/collectors.md`.
- HTTPS only for sources, with a timeout (already in `http_client()`) and a bounded response size.
- Collected URLs are untrusted data: only `http`/`https` are accepted (rejecting `javascript:`, `data:`, `file:`…). They are never opened automatically. If that ever changes, SSRF protection is required (block private and local IPs).
- Secrets (LLM API key, SMTP, webhook) only in environment variables (`.env` ignored by git locally) or GitHub secrets. Never in the code, the config, `.env.example` or the logs.
- LLM endpoint: HTTPS, **only exception**: `http` to `localhost`/`127.0.0.1`/`::1` for a local model (Ollama). Enforced by `is_allowed_llm_url()`.
- YAML: always `yaml.safe_load`, never `yaml.load`.

**Prompt injection: all collected content is data, never an instruction**
- At parsing time (collectors): conversion to plain text, removal of invisible or control characters (zero-width, bidi, etc.), truncated length, validated URL.
- At prompt time (Evening 2): the content is isolated in a clearly delimited block. The system prompt explicitly says that this block is data to evaluate and that any instructions it contains must be ignored.
- Structured (JSON) and validated LLM output: integer score bounded 0-10, summary of bounded length. If the output is invalid, the article is rejected, not guessed.
- The scoring and summary LLM has **no tool and no action**. It only produces text. **Enforced by the code**: `LlmClient` refuses the `tools`/`tool_choice`/`functions`… options (`TypeError`) and rejects any answer containing a tool call (`LlmError`). Never `eval`/`exec`/`subprocess`/`pickle` on external data or on an LLM output; SQL always parameterized.
- Local Ollama: listens only on `127.0.0.1` (default, `OLLAMA_HOST` not set). Never expose it on the network.
- Prompt construction (scoring): re-clean every external field with `clean_text()` + max length (mandatory for `extra`), neutralize the delimiter (`</article>`) in the data, bounded lists (5 tags max), article data **only** in the `user` message, never in the `system` one.
- The LLM output is untrusted too: it is escaped in the HTML or Markdown digest (no injected link or HTML).
- A heuristic detection ("ignore previous instructions"…) may flag suspicious cases in the logs, but it is never relied upon alone.

6. ✅ The entry point that orchestrates everything (a broken source must not block the others) + the content of `interests.yaml`.

### Evening 2 — The agent loop (scoring + summary) ✅
_Finished on 2026-10-05. Deviation from the plan: the summary says **what the article brings**, the scoring reason says why it concerns me; threshold `>= 8`._
- Scoring prompt: my profile + the article → relevance score 0-10 + short justification.
- Summary prompt: 2-3 sentences, *why it is relevant to me*.
- Loop: for each unprocessed article → score → if score > threshold → summary → save.
- Handling of API errors and basic rate limiting.
- End: I can query in SQL "the 5 best of the day".

### Evening 3 — Memory, dedup, delivery
- Cross-source dedup (normalized URL / hash, or even title similarity).
- Statuses so that an already-sent article is never sent again.
- Generation of a digest (Markdown/HTML), sent by email or Discord webhook.
- Daily automation with GitHub Actions (`uv sync` in the runner).
- End: I receive my first automatic digest.

### Evening 4 — Feedback and adaptation (the real "agent" touch)
- 👍/👎 feedback on the articles received (CLI, small page or reaction to the email).
- Feeding the feedback back into scoring (few-shot with my past preferences, or stored criteria that evolve).
- Bonus: detection of "hot topics" (a theme that comes back during the week → deep-dive suggestion).

## Decisions

Approved architecture choices, with their reason. One line per decision.

- `data/` (generated SQLite database, ignored by git): tracked via `.gitkeep` **and** recreated by the `storage/` module if missing, as a guard. To code at step 3.
- `Article` is a `dataclass` (not Pydantic): standard library, enough for now.
- `Article` describes **what the collection brings back**, before any LLM processing. Required fields: `source`, `title`, `url`. Optional (`None`): `author`, `content` (`None` = post without text), `published_at` (not all sources have a date). Automatic: `fetched_at` (UTC, via `default_factory`).
- Dedup by **plain normalized URL** (no hash: easier to debug; no UUID: random, does not detect duplicates). `url` stays the original URL (digest link); the normalized key is a **computed property** of `Article` (never out of sync). In the database: technical id `INTEGER PRIMARY KEY` + `UNIQUE` key column.
- Source-specific info (HN points, GitHub stars…) in `extra: dict[str, Any]`, so as not to pollute the common model.
- Code split: I code the "agent" part myself (scoring, summary, loop, selection, feedback). The presentation (HTML rendering of the digest) can be delegated to Claude. The plumbing (SQLite storage…) can be written by Claude when I ask; I review it.
- SQLite schema: dates as ISO 8601 `TEXT` (readable, sortable), `extra` as JSON `TEXT`, `score INTEGER` (0-10) and `summary TEXT` at `NULL` as long as the LLM has not gone through. Insertion via `INSERT OR IGNORE` on `normalized_url`. Default database: `data/tech_radar.db` (path relative to the launch folder).
- Generic, config-driven collectors (the agent could serve something other than tech watch): abstract class `Collector` (`collect() -> list[Article]`), registry `COLLECTOR_TYPES`, `build_collector(dict)` passes the options to the constructor. Instance `name` = `Article.source`. Unreachable source → exception; failing item → logged and ignored. See ADR 0006.
- Security enforced by construction: `Article.__post_init__` cleans `title`/`author`/`content` (NFKC, hidden characters removed, truncation 300/100/3000) and rejects non-`http(s)` URLs (`ValueError`, the item is ignored). Collectors download only through `fetch()`/`fetch_json()` (HTTPS, 5 MB max), never `client.get`. `extra` is not cleaned: go through `clean_text()` before putting it in a prompt.
- GitHub: official Search API (recently created repos, sorted by stars) rather than scraping the trending page. RSS: one config entry per feed, each with its `name` and `limit` (useful for arXiv, very noisy).
- Orchestration: config validated entirely before any network call (fail fast); then each source is isolated (`except Exception` only at this level); save after each source. Sources run sequentially (~7 s for 17, enough). Paths relative to the launch folder.
- LLM: a single client in the OpenAI chat completions format (`POST {LLM_BASE_URL}/chat/completions`) via `httpx`, without SDK. Local (Ollama) or remote depending on `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`, no "mode" variable nor `if local`. Environment-dependent settings also as variables: `LLM_REASONING_EFFORT` (optional), `LLM_REQUEST_TIMEOUT` (default 30). Criterion: a value that changes depending on where the agent runs goes in the env, otherwise it is a code constant. `.env` loaded by `uv run --env-file .env` (no python-dotenv). See ADR 0008.
- Profile: interests as `id: description` (short and stable id, returned by the LLM and stored; free description, read by the LLM). Priorities are context for the LLM, the code does not compute the score with them. `profile.language` = language name in plain words (default English); prompt instructions in English. See ADR 0009.
- Evening 2 split: Claude does the plumbing (settings, security, `.env`), I code the LLM client, the scoring, the summary and the loop.
- Tests: pytest (dev only), no other test dependency. Network simulated by `httpx.MockTransport` (fixture `fake_http`, which keeps the real settings of `http_client()` and the real checks of `fetch()`), real network blocked by the autouse fixture `no_network`. `main()` tested with a fake collector type registered in `COLLECTOR_TYPES`.
- LLM results (`score`, `reason`, `interests`, `summary`) **only in the database**, not in `Article` (which describes what the collection brings back): the loop receives them from `Scorer`/`Summarizer` and writes them with `save_score`/`save_summary` using the `StoredArticle` id.
- Loop: `LLM_*`/`AGENT_*` settings read **after** the collection (a missing LLM config never costs the collection); retry only if a new attempt can give something else (temperature 0 → invalid answer = no new attempt; server outage = 2 retries then stop). Invalid summary → score kept without summary (A); stop during the summary → nothing saved, article picked up at the next run (D); only **scoring** failures count towards the 5 in a row. Codes: 3 = scoring skipped or stopped, 1 takes priority over 3. See ADR 0019 and 0021.
- Digest (ADR 0023): candidates = scored ≥ threshold, not sent, within the age window; **reading-time budget** (config `digest.reading_time_minutes`, 5 by default) rather than a number of articles, cost by words (200 words/min + 3 s per entry), common budget for entries with and without summary; greedy selection **score descending then oldest first**, what does not fit is skipped and we go on, at least one entry; a larger budget can give **fewer** entries (the best, longer ones): intended. `mark_sent` only after a successful sending. Empty day: one-line report if `digest.send_empty_report` (`true` by default).
- Git workflow: `feature/<kebab-name>` branches via `git flow feature start`, pushed then merged into `dev` **through a GitHub MR** (no `git flow feature finish`, which merges locally). **Merge method: `feature/…` → `dev` with "Squash and merge"; `dev` → `main` (release) with "Create a merge commit", never squash** (a release squash makes the histories diverge: the v0.3.0 release, PR #25, was squashed → `main` (`d750aeb`) outside `dev`'s history, common ancestor stuck at v0.2.0 → conflicts guaranteed at the next release; fix: merge `main` into `dev` once, as a merge commit, 0 file changed). **Always check that the PR base is `dev`** (incident of 2026-10-05: PR merged into `main`; fixed by a revert on `main` + squash into `dev`).
